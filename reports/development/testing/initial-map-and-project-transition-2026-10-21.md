## 대상과 방법

사용자가 제보한 ① 처음 열 때 바다·육지·기타 요소가 따로 나타나는 현상과 ② 새 프로젝트 생성 중 흰 지도 화면을 조사했다. 제품 동작 코드·저장 형식·지도 자료는 수정하지 않았다. 작업용 보고서는 상설 UI 워크트리에 두며 기존 미완성 변경을 보존했다.

실제 배포 웹과 main을 제공하는 로컬 웹 편집기를 Windows Chromium/D3D11에서 실행했다. Windows WebView2 앱은 갱신한 실제 실행 파일과 기존 실행기를 사용했다. 별도 WebView 프로필을 환경 변수로 지정하고 실제 자식 프로세스의 `--user-data-dir`도 해당 증거 폴더인지 확인했다. 앱의 기존 사용자 프로젝트를 대상으로 생성 작업을 하지 않았다.

브라우저/WebView에서 WebGL draw, 준비 상태, 프로젝트 세대, 네트워크 완료, 긴 메인 스레드 작업과 화면을 기록했다. 로컬 편집기는 진단용 응답 치환으로 기존 함수 경계에 타임스탬프만 추가했다. 뒤의 대조 실험도 응답 치환이며 저장소 제품 소스 변경이 아니다. 시간은 계측한 이 PC의 단일 실행값으로, 일반적인 사용자 기기의 소요 시간 보장이 아니다. 앱 초기 수치는 진단용 재로딩이며 최초 프로세스 기동 시간과 구분한다.

## 1. 처음 열 때 요소별 표시 시차

**부분별 점진 로딩은 현재 구조의 결과다. 다만 안정된 기본 지도 없이 요소들이 따로 나타나거나, 지형 요청 자체가 늦게 시작되는 부분은 개선 대상이다.**

- 바다와 육지의 높이·음영은 **같은 DEM 타일**을 사용한다. 둘의 높이 데이터를 별도 파일로 다운로드하는 구조는 아니다. `gpu-base-scene-pass.js`가 같은 준비 타일을 바다 패스와 육지 패스로 그린다.
- 바다는 DEM의 수심에서 색을 계산하지만 육지는 별도의 `tint.webp`를 사용한다. 색상 이미지가 준비되지 않았을 때는 `gpu-terrain-preparation.js`의 중립 회색 1×1 텍스처가 사용되므로 바다에 색이 있어도 육지는 아직 회색일 수 있다.
- 육지 바탕 폴리곤, 영토 채움·경계, 지명, 수계도 서로 다른 소유자와 준비 경로가 있다. 지명이 먼저 나타나는 것이 육지 형상 다운로드 완료를 뜻하지 않는다.
- 밝은 테마의 기본 바다는 `map-theme.js`에서 흰색이다. 지형이 오기 전의 흰 바다와 수심 색이 그려진 뒤의 바다가 달라 보여 로딩 시차가 더 크게 느껴진다. 정치지도와 지형지도의 의도한 색을 구분해야 한다.
- `viewer-composition.js`의 `open()`은 프로젝트 교체, 육지 바탕, 정밀 `map.update()`, 검색 준비를 기다린 뒤에야 `map.loadPhysicalResources()`를 호출한다. `viewer-map.js`는 초기 `allowPreview:false`와 정밀 메시 준비를 사용한다. 따라서 지형 manifest·색상·타일 요청이 정밀 프로젝트 표시 뒤로 밀린다.

교정한 실제 웹 관측(`canonical/viewer.json`)에서는 객체 열기 완료 약 **22.10초**, 현재 화면의 실제 렌더러 준비 완료 약 **24.25초**였다. 최종 가시 타일 12/12, 색상 준비 완료, 오류 0개를 확인했다. 초기 화면 캡처에는 그 이전의 흰 지도 영역이 남아 있다. 바다·육지의 첫 DEM draw도 같은 프레임에서 각각 호출됐으므로 서로 전혀 다른 높이 로딩이라고 설명하면 부정확하다.

초기 진단 스크립트는 부분 갱신되는 `window.__PANDOLAB_GPU_METRICS__.mapReadiness`를 완료 조건으로 사용해 잘못 시간 초과했다. 실제 화면에는 준비 완료가 표시돼 있었고, 렌더러 소유자의 `rendererStats().mapReadiness`를 직접 읽도록 진단을 고쳐 정상 완료를 확인했다. 앞의 진단 시간 초과를 제품의 영구 로딩 실패로 집계하지 않는다.

## 2. 새 프로젝트의 흰 화면

**사용자에게 의도한 동작은 아니다. 기존 코드 주석도 이전 화면을 유지하다 준비된 새 프레임으로 교체한다고 명시하지만, 현재 실행은 그 계약을 지키지 못한다.**

| 관측 | 로컬 웹 편집기 | 실제 Windows WebView2 |
| --- | ---: | ---: |
| 내장 지도 생성 중 렌더 차단 구간 | 약 3.28초 | 약 3.49초 |
| 차단 중 정밀 메시 | 메모리에 유지 | 메모리에 유지 |
| 화면 | 육지 채움 소실·지명 잔존 재현 | 동일 현상 재현 |
| 페이지 오류 | 0개 | 0개 |

`stack/editor.json`과 `native.json`에 상태 경계를, `stack/editor-new-builtin-1.png`와 `native-new-builtin-1.png`에 실제 공백을 기록했다. 이는 모든 기기의 흰 화면이 정확히 이 시간이라는 뜻은 아니다.

`project-domain.js`는 Core의 기존 복구 캡슐을 확보한 뒤 렌더 세대를 먼저 바꾸고 `loadBaseline()`을 실행한다. `gpu-map-renderer.js`의 reset은 `preserveBuiltinMesh:true`여도 렌더를 차단하고 이전 장면·선택·경계 상태를 무효화한다. 장면 캐시는 새 프로젝트 세대의 장면으로 사용할 수 없다. 그런데 `renderWebGl()` 전체에는 차단 시 진입을 막는 조건이 없고 base scene 제출만 차단된다. **GPU 자료 보존과 실제 표시 프레임 보존이 서로 다르다.**

그 차단 구간에 기존 호출이 계속 들어오는 것이 화면 공백의 직접 경로다. 같은 로컬 웹 진단에서 `renderWebGl()` 진입 시 차단된 프레임을 건드리지 않도록 한 조건만 임시 추가하자, 생성 중 기존 국가 채움이 유지됐다(`freeze/editor-new-builtin-1.png`). Core 교체 시간은 그대로였으므로 다운로드 가속으로 공백이 사라진 것이 아니다. 이 대조는 원인과 해결 방향 확인이며 제품 수정 완료나 App 수정 검증으로 간주하지 않는다.

생성 시간 자체의 비용도 별도로 있다. 로컬 웹의 `loadBaseline()` 경계는 두 실행에서 **2.70–2.86초**, 긴 메인 스레드 작업 한 건은 약 **1.46초**였다. 이 경계에는 Core 응답과 현재 읽기 모델의 투영·복사가 포함되며, C++ 연산만의 시간으로 단정하지 않는다. 빈 지도 생성도 관측했지만, 영토가 0개인 정상 결과와 전환 중 흰 공백을 구분했다.

## 제안하는 수정 순서와 경계

1. **새 프로젝트 전환의 화면 연속성부터 수정한다.** 기존 프로젝트 교체·복구 캡슐·렌더러·장면 캐시 안에서 처리한다. 준비 중에는 마지막으로 표시한 지도와 지명을 한 묶음으로 유지하고 입력을 제한한다. 새 프로젝트의 첫 표시 프레임이 준비되면 바탕·영토·지명을 같은 세대로 교체한 후 완료를 알린다. 이전 장면은 전환 중 읽기 전용 표시로만 허용하며 새 프로젝트의 선택·편집·조회 자료로 인정하지 않는다. 창 크기/DPR 변화나 컨텍스트 손실에서도 유지할 수 있는지 확인해야 하므로 임시 early-return 한 줄만 최종 해결로 채택하지 않는다.
2. **최초 기본 지도를 먼저 완성하고 나머지를 덧붙인다.** `viewer-composition.js`·`viewer-map.js`·`physical-resources.js`에서 전역 manifest/육지 바탕/기본 지형 준비를 프로젝트 정밀 처리와 겹친다. 초기 뷰가 정해지면 필요한 가시 타일만 준비한다. 기존 렌더러의 base scene 소유자가 국가 메시 없이도 바다와 육지의 기본 바탕을 한 프레임으로 표시하도록 한다. 물리적 육지 바탕을 역사 영토나 편집 가능 데이터로 취급하지 않는다. 지형지도에서는 투영 영역 안의 바다 바탕과 육지를 함께 제공하고, 정치지도는 기존 색 의미를 유지한다. 색상·음영이 준비되면 묶어 갱신하고 경계·지명·수계를 순서 있게 추가한다. 전체 최고 해상도나 모든 보조 요소를 기다리게 하지 않으며 이전에 확정한 배율·정밀도 규칙은 유지한다.
3. **교체 소요 시간과 UI 정지를 별도로 줄인다.** `core-document-runtime.js`·`core-document-client.js`·`core-document-read-model.js`의 기존 경계에서 Core 처리, 반환값 직렬화, 읽기 모델 수용·복사를 나눠 잰다. 현재 불변 형상의 반복 복사를 줄이거나 큰 투영 처리를 나눌 수 있는 지점을 수정한다. Core가 받아들인 상태의 원자성과 기존 Undo/저장/복구는 보존하며 별도 프로젝트 원본이나 병렬 상태 관리자를 만들지 않는다. 아직 세부 비용은 분리 측정하지 않았으므로 특정 내부 함수만이 2.7초의 전부라고 단정하지 않는다.

주요 변경 대상은 위 기존 소유자들과 `app-project-restore.js`·`rendering-domain.js`의 전환 연결이다. 프로젝트에 시간 탐색·비교 기능을 추가하는 작업은 포함하지 않는다.

## 구현 후 통과해야 할 검증

- 차가운 캐시와 재실행, 느린 DEM·색상·육지 바탕·경계 응답을 각각 재현한다. 기본 바다·육지가 함께 나타나고 나머지가 늦더라도 기본 지도는 사라지지 않아야 한다. 준비 전 기본 바탕을 정밀 자료 완료로 표시하면 안 된다.
- 새 프로젝트의 실제 준비 경계를 지연시켜 이전 프레임 보존, 새 프레임의 동일 세대 바탕·영토·지명, 완료 후 이전 객체 잔존 없음과 선택 일치를 화면·모델 양쪽으로 확인한다.
- 내장/빈 지도, 기존 편집·초안·Undo 이력, 생성 실패·복구, 중복 생성, 창 크기·DPR 변화·컨텍스트 복구를 검사한다. 렌더 차단과 Core 처리 시간이 줄었는지는 따로 측정한다.
- 완료는 기존 소유자의 현재 상태와 실제 표시 프레임으로 판단한다. 부분 갱신된 진단 객체나 단순 다운로드 종료만 사용하지 않는다. WebGL1·2·Canvas의 관련 경로와 Windows WebView2를 각각 확인하고, 모바일 레이아웃 검사와 실기기 검증을 구분한다.

## 판정과 미실행 범위

원인 조사와 대조 실험까지 완료했다. 제품 수정·회귀 테스트 추가·main 통합·재배포·앱 재빌드는 이번 조사에서 하지 않았다. Android·모바일 실기기·실제 사용자 사용성 검증과 역사 GIS 정확도 검증도 하지 않았다. 새 프로젝트의 흰 화면 개선과 최초 기본 지도 개선은 위 순서로 진행하는 것을 권고한다.
