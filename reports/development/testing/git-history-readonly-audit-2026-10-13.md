## 3. 기존 `Pando` 저장소에 바로 강제 푸시할 수 없는 이유

GitHub의 `refs/pull/*`은 일반 사용자 브랜치가 아닌 플랫폼 관리 참조다. 위 86개의 PR tip은 구형 타일 파일을 현재까지 직접 보유하며, 그 commit ancestry 역시 현재 삭제된 객체를 보존할 수 있다. `main`과 `work/*`를 force-push하더라도 PR 참조에서 이전 객체로 접근할 수 있으므로 GitHub 서버 GC가 이 파일을 제거한다고 기대할 수 없다.

[GitHub 공식 문서](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository)는 과거 PR 참조 및 서버 GC 처리가 필요하다는 점과, **민감 정보가 아닌 일반 파일을 제거하기 위해서는 GitHub Support가 제거 작업을 지원하지 않는다**는 점을 명시한다. 이 작업은 대용량 정상 지형 데이터이므로 해당 지원을 받는 것으로 계획할 수 없다.

따라서 **현행 저장소에 대한 강제 푸시는 실행하지 않음**. 기존 커밋 주소·배포·로컬 워크트리를 모두 바꾸면서 목표 용량 감소를 달성하지 못할 수 있기 때문임.

## 4. 실제 용량 절감을 위한 안전한 이전 절차

1. 별도 신규 GitHub 저장소를 준비하고, 기존 `Pando` 원격은 온전한 역사 백업으로 유지. 새 저장소에는 기존 PR 참조를 가져오지 않는다.
2. 같은 이력 필터를 사용하되 재작성된 `refs/heads/*`와 `refs/tags/*`만 새 저장소에 푸시. `git push --mirror`는 플랫폼 PR 참조 때문에 사용하지 않는다.
3. 각 브랜치의 최종 트리 SHA·현행 지도 데이터 SHA를 기존과 일치시키고, 필요한 Web/Native CI·Pages 무결성 검증 실행.
4. 공개 서비스의 URL 유지가 필요하면 기존 `Pando`를 보관용으로 재명명한 뒤 정리본에 기존 이름을 부여하는 방식을 **별도 전환·롤백 계획**에 따라 수행. 기존 페이지의 URL이 자동 유지된다고 가정하지 않는다.
5. 모든 검증 완료 전에는 원본 저장소 삭제, 원본 브랜치 강제 푸시, 원본 Git 이력 수정 금지.

현재 연결된 GitHub 도구에는 **신규 저장소 생성/이름 변경** 기능이 없어 새 저장소를 실제로 만들거나 서비스 이름을 교체할 수 없다. 신규 목적지가 확보되기 전에는 이 보고서를 안전한 완료 지점으로 삼는다.
