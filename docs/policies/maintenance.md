# 정책 문서 유지 관리

분야별 탐색 페이지는 기존 원본을 가리키는 **색인**입니다. 실제 규칙·코드·검증 계약을 여기로 복사해 두 번째 정본을 만들지 않습니다.

## 변경할 때

1. 먼저 [중앙 안내](README.md)와 분야별 페이지에서 **현행 정본**을 찾고, 선언된 정책과 과거 작업 기록을 구분합니다.
2. 정책의 의미를 바꿀 때는 실제 정본 원문에서 수정하며, 다른 문서는 링크·효력 상태만 갱신합니다. **실행 규칙**은 해당 `src/`·`tools/`·`config/`·`scripts/contracts/` 소유자가 담당합니다.
3. 원본 경로를 꼭 옮겨야 한다면 소비자·상대 링크·CI 계약을 함께 갱신한 뒤 실제 호출·출력의 정합성을 확인합니다.
4. 옛 스키마·이전 앱·과거 검사 기록을 현재 정책이라고 표기하지 않고, 현행 계약과 구분합니다. `prototype`·`staged`를 별도 승인 없이 production으로 승격시키지 않습니다.
5. 분야별 페이지에 문서·코드·계약의 **실제 경로를 Markdown 상대 링크**로 연결하고, 검증 그룹은 `check-group:<id>`, 등록된 npm script는 `check-script:<name>`으로 적습니다.
6. `pnpm check:policies`로 정책 색인·직접 연결 원문의 내부 링크, 코드/계약 위치 및 검증 그룹·스크립트 존재를 확인합니다. 이 명령은 **전체 `docs/**/*.md` 문서의 상대 링크·사라진 코드 경로도 감사**하고, 중앙 색인에 직접 연결되지 않은 과거 기록의 문제를 감사 경고로 보고합니다. 모든 과거 링크를 엄격하게 실패 처리하려면 `node scripts/check-policy-links.mjs --strict-all`을 사용하며, 해당 모드는 보존된 역사 기록 때문에 실패할 수 있습니다. 기능이 변경된 경우에는 별도로 해당 제품 검증 그룹을 실행합니다.

## 검증의 한계

정적 정책 검사는 Markdown 링크·Git 트리에서 접근 가능한 **파일 경로**, `scripts/contracts/application-checks.json`의 그룹 ID 및 `package.json`의 스크립트 이름을 확인합니다. 코드의 런타임 의미, 외부 URL 도달성, GitHub 헤딩 앵커 의미, 과거 검증의 진위, GIS 정확도를 자동으로 입증하지 않습니다.
